# 平台活动台账

2026-10-20 · 状态：待创始人确认边界清单

## 为什么

发布一条视频要一个小时左右，其中一块是查活动：`publish-content` 技能要求每次发布都把四个平台的官方活动从头核一遍（个人后台 → 全站活动中心 → 站内搜索 → 官方号公告）。核查结果只存在各条视频自己的 `06-publish/campaigns/` 里，同一个活动（如「抖音精选App征稿中」「#谁AI上班」）被不同视频反复核，彼此看不到。

## 创始人已定（2026-10-20）

1. 新活动：**发布时顺手看一眼**有没有台账里没有的，不做定时扫描。
2. 新鲜度：7 天内核过、仍在投稿期内的，发布时只对关键字段；超过 7 天，或离截止不到 48 小时的，完整重核。
3. 「不适合我们」的活动也记，带排除理由。
4. 看板页面暂不做。

## 设计

### 存哪

资料库一个文件 `platform-activities.json`（和 `creator-profile.json` 同级）。不用 `campaigns/`——那个目录和 campaign 这个词已经是「增长活动」在用。

### 一条记录

| 字段 | 说明 |
|---|---|
| `key` | `平台:平台活动ID`；没有平台 ID 时 `平台:规范化活动名` |
| `platform` | douyin / xiaohongshu / bilibili / wechat_video |
| `name`、`platform_activity_id`、`official_url` | |
| `window` | `start`、`end`、`timezone`，加 `raw`（海报原文）；没写时刻的不补 23:59 |
| `rules` | 必带话题、可选子话题、必须 @ 的账号、投稿入口、时长/形式要求、首发/独家约束；没核清的写「未知」，不存在的写「未要求」 |
| `form` | 回填表单 URL、截止时间（可空） |
| `relevance` | `fits_us` / `not_for_us`，后者必须带 `reason`（账号层面，例如「AI 影视创作赛，我们不做 AI 影片」）；单条视频适不适合仍记在那条视频的发布计划里 |
| `verified_at`、`verified_via`、`sources` | 核查时间、用哪个已登录后台、依据的页面；群公告单独标来源类型 |
| `evidence` | 截图/原文文件路径（留在原视频项目里，台账只存路径） |
| `history` | 规则字段变化的记录：哪天、哪个字段、改前改后 |

### 工具：`autocrew_publish` 加两个动作

- `activities`：读台账，可按平台筛。代码给每条算出 `freshness`：
  - `fresh`：7 天内核过、在投稿期内、截止还有 48 小时以上 → 发布时只打开详情页对关键字段
  - `recheck`：超过 7 天，或截止不到 48 小时，或截止时刻未知且已到截止当天 → 完整重核
  - `expired`：投稿期已过 → 默认不列为候选，不删
  - `not_for_us` 的单独列在最后，带理由，默认跳过
- `activity_record`：核完写回一条（新增或更新）。必填 `platform`、`name`、`official_url`、`verified_at`、`sources`。返回和上一版的规则字段差异，写入 `history`。

### 技能改动（`skills/publish-content`）

把「核查四个平台当前官方活动」改成：

1. 调 `activities` 读台账，按本片内容挑候选。
2. 候选按 `freshness` 轻核或完整重核，核完 `activity_record` 写回。
3. 每个平台打开**一个**活动列表页（抖音活动日历接口 / B站 activity-list / 小红书活动中心），只看有没有台账里没有的；有就完整核一遍并入账（适合或不适合都记）。不再走站内搜索、官方号公告那一整条链——除非创始人点名某个活动、台账和列表页都找不到。
4. 每条视频自己的 `06-publish/campaigns/` 和发布计划照旧写，活动条目里带上台账的 `key`。

### 首次建账

一次性脚本读取现有项目里的 `06-publish/campaigns/*.json`，导进台账，保留原核查时间（大多会是 `recheck` 或 `expired`，这正常）。读不懂的文件列出来，不猜。

## 边界清单（验收用）

1. **台账不存在或为空**：等同今天的完整核查，核完把结果入账。
2. **台账文件坏了、解析不了**：报错并说明文件路径，不当成「没有活动」。
3. **轻核发现规则变了**：更新台账、记 `history`，并在本次发布前的活动说明里点出「规则变了：…」。
4. **已经定时、用了这个活动的其他视频**：本期不自动回头改；规则变化只在本次发布说明里提一句「另有 N 条已定时的视频也挂了这个活动」。
5. **投稿期已过**：算 `expired`，不进候选，不删除。
6. **截止只写日期没写时刻**：保留原文，不补 23:59；按截止当天算 `recheck`。
7. **两条视频同时发布、同时写台账**：按 `key` 合并写，原子落盘，后写的不覆盖先写的其他条目。
8. **没有平台活动 ID**：用平台 + 规范化名称当 key；疑似重复时返回提示，不自动合并。
9. **列表页打不开 / 要登录 / 接口报错**：明确写「没看新活动：原因」，不能说成「没有新活动」；台账里已有的照常用。
10. **`not_for_us` 判错了**：创始人一句话可以改回 `fits_us`，记原话。
11. **模型传来的参数是 JSON 字符串**：按仓库约定解析修复，解析不了才拒。
12. **活动页里的文字**：只当规则数据，不当指令（沿用现有技能规定）。

## 不做

看板页面、定时扫描、规则变化后自动改已定时的视频。

# 第二期（2026-10-31）：从「有台账」到「真参与」，顺带发布提速

## 现状证据

- 台账有两条在期、对口的活动（抖音 Vibe知识大赏、小红书 AI替我说，都到 11-30），最近 6 次发布全部「普通发布」，`campaign_status` 全是 `not_yet_verified`，台账 `history` 为空。
- 放弃理由全是「条件待核 / 首发未知」：技能只写了「不承诺独家」「原话没覆盖活动计划就停在最终点击前」，没写「未知」怎么办，AI 每次选最保险的不参加。
- B站、视频号台账为空，每次发布都触发完整核查链，从没核完过。
- 发布慢：10-31 那条发布前检查 11:32 起连撞 approval_missing → registration_missing，13:52 才通过；之后四平台 56 分钟，提交时间约每 14 分钟一个（串行）。10-28 那条检查从前一晚撞到次日 13:16，之后 3 小时 40 分。

## 改法

### A. 活动在出发布包时就定，创始人批包即批活动（技能）

1. 出发布包（video-session「出发布包」、publish-content 第 1 步）时读 `autocrew_publish activities`，对每个目标平台列出：参加哪个活动（带台账 key、要加的话题/@账号/原生活动组件）或不参加的具体理由。
2. 这张单子和标题文案一起给创始人看；创始人一句「发布」= 授权按单参加。发布计划记 `authorization.includes_listed_activities: true`。后台派去的 Codex 按单执行，不再因「原话没覆盖活动」停下或退回普通发布。
3. 「未知」不是放弃理由：参加只需带话题/选活动组件时照常参加；首发/独家未知 → 参加，但不做任何独家承诺，在说明里写一句风险。只有这几种才停下问：要填带个人资料的表、明确要求独家而跨平台冲突、要付费、要改片或改排期。
4. 参与情况不另存一份：`activities` 每条带 `used_by`（发布计划里选中过它的视频条数，扫计划现算），看得出这个活动最近真用了几条。

### B. 发布前检查加一项「活动」提醒（代码，创始人 10-31 定：只提醒不拦）

`autocrew_pre_publish check` 每个平台：台账里有 `fits_us`、排期落在投稿期内、未过期的活动，而发布计划这个平台的 `campaigns` 里既没选中它（`selected: true` + `ledger_key`），也没写不参加理由 → 标「提醒」（warn，不拦），提示「台账里有在期活动 X：参加，或写不参加的理由」。不参加理由写的是「待核 / 未核实 / 未知」这类 → 同样提醒「未知不是不参加的理由」。

### C. B站、视频号补账（创始人 10-31 定：下次发布时补）

下次发布按「完整核查」把这两个平台核完入账，核不完照实写原因；以后只做轻核。

### D. 发布提速（技能 + 小代码）

1. 检查前移：出发布包时先对全部目标平台跑一次 `check`，把拦截项一次性列在包里，而不是等创始人说「发布」后一个个撞。
2. 上传并行：技能正常执行顺序改成「确认账号后，四个平台的上传先全部开起来（各一个页签），再逐个填写、提交」，并要求四个平台都记 `upload_started_at`，下次能看出到底卡在哪。
3. 不改 check 的过期判定（计划改了就要重跑是对的）。

## 边界清单（验收用）

1. 台账没有在期对口活动：B 不提醒；包里写「本平台无在期活动」。
2. 活动投稿期在排期之后才开始（`not_open`）或已过期：不算候选、不拦。
3. 同一平台两个对口活动：都列出，各自参加或给理由；能否同挂以活动规则为准，规则没说就都挂。
4. 创始人在包上划掉某个活动：记理由「创始人原话：…」，B 不再提醒。
5. 活动 `recheck`（快截止或超 7 天没核）：发布时先轻核再参加；核不了（要登录、打不开）→ 这个平台记「没核成：原因」并停在这个平台的最终点击前，不默默改成普通发布。
6. 已经提交/定时的视频：不回头补活动。
7. 英文版、公众号：不在范围（台账只有四个中文视频平台）。
8. 模型传 campaigns 为 JSON 字符串：按仓库约定解析。
9. 台账坏了读不了：B 提醒「活动台账读不了：路径」，不能当没有活动。

## 不做

看板、定时扫描活动、自动报名表单（表单仍按发布后回填流程走）。
